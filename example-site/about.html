How it works

The mechanism, and the two places it is not what you would first design.

The shape of it

The gate is a static page. There is no application server anywhere in the design, and adding one would defeat the point — a backend is a host, and a host is the thing being removed from the picture.

  1. The address lives in the URL fragment (https://gate/#<magnet>). Browsers never send a fragment to the server, so whoever hosts the gate does not learn which site you opened. The gate's operator cannot keep a log they never receive.
  2. A BitTorrent client runs in the page. It has to be in the page: a service worker cannot open the WebRTC connections that reach other browsers.
  3. A service worker serves the site from the swarm at /webtorrent/<infohash>/…. Every request the site makes — stylesheets, images, fonts, nested frames — is a fetch this worker answers.
  4. The site renders in a sandboxed frame, under a policy the worker attaches to every response.
  5. If the site carries a signature, it is checked first, file by file, against the list its author signed — before the frame is shown and before any author is named.

Step 3 is why the gate never rewrites a site's HTML or invents custom tags to load its images. A service worker sees every request its pages make, so there is nothing for a rewriting scheme to overlook — and the response headers, where the security policy lives, are ours to set.

Two things that are not what you would design

Sites share the gate's origin, and they must. The obvious design is a fully sandboxed frame with an opaque origin. Browsers refuse: a document with an opaque origin is never controlled by a service worker, so it loads nothing at all — not the page, not one stylesheet. Since the worker is how sites are served, sites live on the gate's origin, and isolation comes from the sandbox flags and the policy instead.

One site is kept out of another's files by the worker, not by the policy. The first version pinned every policy source to that torrent's own path and leaned on the browser to enforce it. One major browser enforced it correctly; another refused a site's own stylesheets under the same rule. A boundary that browsers disagree about is in the wrong place, so the check moved into code we control: before serving a file, the worker works out which torrent is asking, and refuses anything from a different one.

What a published site must look like

A folder with index.html at the top and relative links inside. That is the whole contract. It renders exactly as it would from any static web server, because that is all it is — no build step, no framework, no manifest to write.

The top is meant literally. index.html is the one at the root and nowhere else; the gate does not go hunting for a page buried three folders down and decide that must be what you meant. A site without one is not an error — you get the list of its files and you walk it, the way a directory has always been browsable.

How the folder reaches the gate is up to you: drag it in, hand it a .zip of it, or pick files one at a time. A single page on its own is published as index.html, since a site of one page has nothing else it could be. A .zip is read in the browser and never unpacked to disk — what it holds goes into the swarm directly.

Two more names mean something at that root, and only there: spore.pub, the key a site is published under, and spore.sig, a signed list of every other file with its hash. A signature anywhere else is not a signature. Republishing somebody's site keeps their signature only if it verifies whole; otherwise theirs is dropped and the site goes out as yours. There is no third outcome.

Scripts are off by default and switched on per site, by the reader, after being told what that costs. Sites are documents here; the ones that need to run code should expect to ask.

The uncomfortable parts

Enabling scripts for a site lets it reach the gate's own page, because they share an origin. It still cannot reach the network beyond its torrent, but it could interfere with the address bar above it. Closing that properly needs a second origin for content, which is a later change; until then the toggle asks first and says why.

WebKit is a third. A frame carrying the sandbox attribute is never controlled by a service worker there, however the flags are set, so on iOS the choice is between a frame without the attribute and no site at all. The gate takes neither quietly: it measures what this engine does, explains what is lost — a deliberate click could open a tab elsewhere — withdraws the scripts toggle entirely, and asks before showing anything.

Trackers are the other soft spot. Browsers can only find peers through a few public WebSocket trackers, which is a small number of shared services in a design that is otherwise about not depending on any. They learn which infohash you asked for. They cannot serve you the wrong bytes — the hash settles that — but they are a chokepoint, and an honest description of the system has to say so.
